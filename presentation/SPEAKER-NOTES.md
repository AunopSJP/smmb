## 01 · ปก

**พูด:** “ระบบนี้ไม่ได้เริ่มจาก ‘ทำตู้ให้ฉลาด’ แต่เริ่มจากคำถามง่าย ๆ ว่า —
เราจะพิสูจน์ได้ยังไงว่าเจ้าหน้าที่มาถึงบ้านจริง ไม่ใช่แค่เซ็นชื่อไว้”

- ชี้ว่าทุกบทบาทใช้ **เว็บแอปเดียว** ไม่มีแอปแยก 5 ตัว
- ตัวเลข 99 / 05 / 03 / 02 คือขนาดงาน ไม่ใช่ feature list

## 02 · โจทย์

**พูด:** “สมุดลงชื่อหน้าบ้านพิสูจน์ได้แค่ว่ามีคนเขียน — ไม่ได้พิสูจน์ว่าคนนั้นยืนอยู่ตรงนั้น”

- ยกตัวอย่างการโกง: เอาสมุดไปเซ็นที่อื่น / ให้คนอื่นเซ็นแทน / ถ่ายรูป QR ไปสแกนที่บ้าน
- 3 ความต้องการ: เจ้าหน้าที่ต้องพิสูจน์ได้ · ไรเดอร์ต้องง่าย · เจ้าของบ้านต้องขอความช่วยเหลือได้เร็ว

**ถามห้อง (ถ้ามีเวลา):** “ถ้าเป็นคุณ จะยอมให้อะไรเป็นหลักฐานว่ามีคนมาตรวจ?”

## 03 · หลักคิด — สอง QR

**พูด:** “QR หน้าตู้เป็นกระดาษ ใครถ่ายรูปไปก็สแกนได้ — เราจึงต้องมี QR ที่ออกใหม่ทุก 15 วินาที
และผูกกับงานของตู้นั้น”

- QR ใบที่ 1 = ระบุ **ตู้นี้**
- QR ใบที่ 2 = ระบุ **คนนี้ + เวลานี้**
- เซิร์ฟเวอร์จับคู่ `j` (job) + `u` (officer) + เวลา แล้วตัดสิน
- ตู้ทำหน้าที่แค่อ่าน — **ไม่มีสิทธิ์ให้ผ่านเอง**

## 04 · Flow ตรวจ 60 วินาที

**พูด:** “ทั้งหมดนี้จบในประมาณหนึ่งนาที”

1. เจ้าหน้าที่สแกน QR หน้าตู้ → server เช็ค 5 อย่าง
2. server สร้าง job อายุ 60 วิ → ตอบ long-poll ที่ตู้ถืออยู่ → ตู้ตื่นทันที
3. ตู้เปิดกล้อง + เสียงปี๊บ → แอปขอ QR ประจำตัว
4. ยื่น QR ให้กล้องตู้ → ผิดได้ 3 ครั้ง
5. server ตัดสิน → pass / retry / fail → แจ้งเจ้าของ

**จุดที่ต้องเน้น:** ขั้นที่ 2 คือเหตุผลที่ตู้ไม่ต้องตื่นตลอดเวลา — ประหยัดไฟแต่ยังตอบเร็ว

## 05 · สถาปัตยกรรม

**พูด:** “ทุกคำตอบมาจาก API ตัวเดียว”

- เว็บ PWA ทุกบทบาท (เจ้าของบ้าน/เจ้าหน้าที่/หัวหน้า/แอดมิน/ไรเดอร์)
- ตู้คุย HTTPS + HMAC ทุกคำขอ
- PostgreSQL เก็บข้อมูลและ log แบบเพิ่มอย่างเดียว
- Redis ใช้แค่ rate limit/lock — ล่มแล้วระบบหลักยังทำงาน
- long-poll อยู่ใน memory (JobHub) → **รัน backend ตัวเดียว** เป็นข้อจำกัดที่รู้ตัว
- ไม่มี MQTT / LINE / OTP / SMS / การชำระเงิน

## 06 · บทบาท

**พูด:** “หนึ่งเบอร์มีหลายบทบาทได้ แต่สิทธิ์ตัดสินที่ route และ server”

- owner: ตู้ที่ผูกไว้
- officer: เฉพาะโซน + ในเวลาตรวจ + ต้องเปิด push
- head: officer + จัดการทุกโซนของหน่วยงาน
- admin: ทั้งระบบ + audit การเปิดดูข้อมูล
- rider: ไม่มีบัญชี ใช้ `/public/*`

**กฎที่ยกมาพูด 1 ข้อ:** เจ้าหน้าที่ตรวจตู้ที่ตัวเองเป็นเจ้าของไม่ได้ — กัน conflict of interest

## 07 · SOS

**พูด:** “SOS ไม่ได้จบที่การแจ้งเตือน — มันไล่ตามคนจนมีคนรับ”

- 0:00 → เจ้าหน้าที่ในโซน
- 0:30 → ทั้งหน่วยงาน + หัวหน้า
- 1:00 → บอกเจ้าของตามตรงให้โทร 191 / 1669
- คนแรกที่กดรับ = ผู้ดูแลเคส (ล็อกที่ server)
- เบอร์/ที่อยู่เห็นเฉพาะตอน SOS เปิด และถูกบันทึกการเข้าถึง
- ไม่ส่งถึงเจ้าของบ้านเอง

**ย้ำ:** SOS ไม่แทน 191 — ระบบบอกเรื่องนี้ตั้งแต่สมัคร

## 08 · ไรเดอร์

**พูด:** “คนส่งของไม่ต้องมีบัญชี ไม่ต้องติดตั้งแอป และเราไม่เก็บตัวตนเขา”

- สแกน QR หน้าตู้ หรือพิมพ์รหัสใต้ QR
- ได้ ticket 10 นาที ใช้ครั้งเดียว
- 5 ครั้ง/ชั่วโมง/ตู้
- เจ้าของเห็นแค่ “มีของมาส่ง + เวลา” ไม่เห็นว่าใครส่ง

**บริบท:** ปุ่มกดหน้าตู้ถูกตัดออก เพราะสึกหรอและถูกกดเล่น — QR/รหัสพอ

## 09 · ฮาร์ดแวร์

**พูด:** “ตู้อยู่ได้ด้วยโซลาร์ เพราะมันหลับเกือบทั้งวัน”

- ESP32-CAM + OV2640 — อ่าน QR แล้วส่งต่อ
- โซลาร์ 2W + 18650 ×2
- หลับลึกนอกเวลาตรวจ · ตื่นก่อนช่วง 3 นาที
- ในเวลาตรวจถือ long-poll 5 นาที
- HMAC ทุกคำขอ + OTA
- ไม่มี LED สถานะ — ใช้เสียงปี๊บ + ไฟส่อง QR

**ข้อจำกัดที่ต้องพูดตรง ๆ:** ยังไม่เคยรันกับตู้จริง — ตัวเลขพลังงานเป็นสมมติฐานที่ต้องวัด

## 10 · ความปลอดภัยและความเป็นส่วนตัว

**พูด:** “เราไม่อยากให้เชื่อคำว่า ‘ปลอดภัย’ — เราอยากให้เห็นว่ามีกฎอะไรและใครตรวจได้”

- ผลตรวจคิดที่ server เท่านั้น
- HMAC-SHA256 + timestamp ±60 วิ + nonce
- log ทุกการสแกน append-only
- ข้อมูลส่วนบุคคลตัดที่ server · mapper ทุก endpoint
- เบอร์/ที่อยู่เห็นข้ามบทบาทเฉพาะ SOS เปิด + audit
- รูป 30 วัน · log 1 ปี · ลบบัญชีพัก 7 วันแล้ว anonymize

**ต้องพูด:** ข้อตกลง/PDPA ฉบับจริงยังต้องให้ผู้เชี่ยวชาญกฎหมายตรวจก่อนเปิดใช้

## 11 · UX / UI

**พูด:** “เป้าหมายคือคนอายุ 70 เปิดครั้งแรกแล้วใช้ได้ โดยไม่ต้องมีคู่มือ”

- 99 หน้าจอ · 3 โหมด (ง่าย/ปกติ/ละเอียด) · ไทย/อังกฤษ
- ตรวจ 390 / 768 / 1024 / 1440
- โหมดง่าย: ปุ่ม ≥ 64px, ซ่อนรายละเอียดรอง
- โหมดละเอียด: รหัสตู้/แบต/เวลา สำหรับทีมเทคนิค
- ตารางมี filter + group
- ธีมแดงหม่น #9A2F36 ไม่ใช่แดงสด

**ชี้:** ภาพหน้าจอเป็นของจริงจาก `ux-redesign/shots` ไม่ใช่ mockup

## 12 · ตัวเลข

**พูด:** “ตัวเลขพวกนี้ตรวจซ้ำได้จาก repo ไม่ได้ประมาณ”

- 99 หน้าจอ (registry เดียว)
- 155 REST endpoints (controller decorators)
- 225 unit tests (113 backend + 112 frontend, รันวันนี้)
- 170 e2e (รายงาน 13 พ.ย.)
- 45 migrations · 41 ตาราง
- 9 Playwright (เบราว์เซอร์จริง)

**ถ้าถูกถามว่า “ทำไม e2e ไม่รันวันนี้”:** ตอบตรง ๆ ว่า unit รันวันนี้ ส่วน e2e อ้างรายงานล่าสุด และ CI ยังไม่รัน e2e (เป็นงานค้าง W-07)

## 13 · สถานะจริง

**พูด:** “ซอฟต์แวร์พร้อม แต่ยังไม่เปิดนำร่อง — และเราไม่ควรพูดว่าเปิดได้”

พร้อม:
- flow 5 บทบาทต่อ API จริง
- production 200 · postgres/redis/push up (ตรวจวันนี้)
- deploy ขึ้น production ได้ + CSP/HSTS
- unit/e2e/Playwright ผ่าน
- งานเบื้องหลังทำงาน

ยังติด:
1. ตู้จริงยังไม่เคยรันกับระบบ
2. Web Push ยังไม่ยืนยันถึงมือถือจริง
3. ไม่มี backup อัตโนมัติ / ไม่เคยซ้อม restore
4. ไม่มี uptime monitor นอกเครื่อง
5. ยังไม่ตัดสินโดเมนจริง (QR พิมพ์แล้วเปลี่ยนยาก)

**ประโยคปิดสไลด์:** “โค้ดพร้อมแล้ว — สิ่งที่ขาดคือการพิสูจน์กับของจริง”

## 14 · Roadmap

**พูด:** “เราไม่ใส่เดดไลน์ปลอม — ใส่ ‘เกณฑ์ผ่าน’ แทน”

- A: ตู้จริง 1 หลัง → ตรวจ 20 ครั้งติด
- B: นำร่อง 1 หมู่บ้าน → 10–20 ตู้ 4 สัปดาห์ ไม่มีข้อมูลหาย
- C: ขยาย → onboarding หน่วยงานใหม่ได้ใน 1 วัน

**หลักตัดสิน:** ความเสถียร → ความเร็วในการพัฒนา → ความสวยงาม
**ไม่ทำในเฟสนี้:** RFID · MQTT · LINE · OTP · ชำระเงิน · auto-deploy

## Q&A ที่มีโอกาสถูกถาม

**ทำไมไม่ใช้ LINE?**
LINE Notify ปิดบริการแล้ว และการผูกระบบความปลอดภัยกับแพลตฟอร์มภายนอกเพิ่มความเสี่ยง/ข้อจำกัด PDPA
เราใช้ Web Push + PWA และบอกผู้ใช้ให้เปิดใน Safari/Chrome ไม่ใช่ in-app browser ของ LINE

**ทำไมไม่มี OTP?**
ตัดเพื่อลดขั้นตอนและลด dependency; ช่องทางรีเซ็ตคือหัวหน้า/แอดมิน
ยอมรับ trade-off นี้ และป้องกันด้วย rate limit + ล็อกบัญชี

**ทำไมตู้ไม่ตัดสินผลเอง?**
ถ้าตู้ตัดสินได้ คนที่แก้ firmware หรือปลอมตู้ก็ผ่านได้
การให้ server ตรวจลายเซ็น/เวลา/โซน/งานคือหัวใจของการกันปลอม

**ทำไมไม่เก็บออฟไลน์แล้วซิงก์ทีหลัง?**
เพราะจะเปิดช่องให้สร้างหลักฐานย้อนหลัง — เรายอมให้ตรวจไม่ได้ดีกว่าปลอมได้

**แบตอยู่ได้นานแค่ไหน?**
ยังไม่วัดกับตู้จริง — เป็นสมมติฐานจาก deep sleep + โซลาร์ 2W
ต้องวัดกับตู้จริงก่อนเปิดนำร่อง (Phase A)

**ใครเห็นข้อมูลส่วนบุคคล?**
เห็นตามขอบเขตบทบาท; เบอร์/ที่อยู่ข้ามบทบาทเห็นเฉพาะตอน SOS เปิด และมี data access log
แอดมินเปิดดูได้แต่ถูกบันทึก

**ต้นทุนต่อตู้เท่าไหร่?**
ยังไม่สรุป — ต้องรอ BOM และผลทดสอบจริง; ไม่ควรเดาตัวเลขในที่ประชุม

**ถ้าเน็ตบ้านล่ม?**
ตู้หลุดเกิน 3 นาทีในเวลาตรวจ → แจ้งเจ้าของ + แอดมิน; ไม่มีการเก็บงานออฟไลน์
SOS ยังทำงานผ่านมือถือเจ้าหน้าที่คนอื่น

**ทำไมไม่ auto-deploy?**
เจ้าของโปรเจกต์ตัดสินว่าซับซ้อนเกินไป; ใช้ `git pull` + `scripts/deploy.sh --migrate` ด้วยมือ
และ repo เป็น public จึงไม่ควรใช้ runner บนเครื่อง production

**ทำไม long-poll ไม่ใช้ MQTT?**
ลดชิ้นส่วนที่ต้องดูแล; ตู้คุย HTTPS อยู่แล้วและได้งานทันที
ข้อแลกเปลี่ยนคือ backend ต้องรันตัวเดียว (JobHub in-memory) — รู้ตัวและมี advisory lock กัน boot ซ้ำ
