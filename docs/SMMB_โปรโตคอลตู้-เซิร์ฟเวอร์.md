## 🧭 สรุปสั้น

| เรื่อง | เลือกใช้ | เหตุผล |
|---|---|---|
| ช่องทาง | **HTTPS (REST)** อย่างเดียว | backend เป็น NestJS อยู่แล้ว ไม่ต้องมี MQTT broker (ตามประชุม : ไม่ใช้ MQTT) |
| นอกเวลาตรวจ | **ตู้เริ่มคุยเอง** : ตื่น → ส่ง 1 ครั้ง → หลับ | ตู้หลับลึก เซิร์ฟเวอร์ติดต่อหาตู้ไม่ได้อยู่แล้ว |
| ในเวลาตรวจ | **Long-polling** : ตู้ถามค้างไว้ "มีงานไหม" เซิร์ฟเวอร์ตอบทันทีที่มีงาน | ปลุกตู้ได้ใน 1–3 วิ โดยยังเป็น HTTP ธรรมดา |
| ปุ่มส่งของหน้าตู้ | **กดแล้วตู้ตื่นเอง** → ส่ง 1 ครั้ง → หลับ (ได้ทุกเวลา) | ไรเดอร์ไม่ต้องใช้มือถือ · ปุ่มปลุกตู้จากหลับลึกได้ |
| รูปแบบข้อมูล | **JSON** | ข้อมูลแต่ละครั้งเล็กมาก (~200–400 ไบต์) อ่านง่าย debug ง่าย ฝั่ง ESP32 ใช้ ArduinoJson |
| ยืนยันตัวตนตู้ | **ลายเซ็น HMAC-SHA256 ทุกคำขอ** (รหัสลับประจำตู้) | ปลอมตู้ไม่ได้ ไม่ต้องขอ token ก่อน = ประหยัดไฟ 1 รอบ |
| กันส่งซ้ำ (replay) | เวลา (timestamp) + เลขสุ่มครั้งเดียว (nonce) | คนดักข้อมูลเอาไปส่งซ้ำไม่ได้ |

## 🔐 1. การยืนยันตัวตนของตู้

**ตอนผลิต / ติดตั้ง**
- เซิร์ฟเวอร์สร้าง **รหัสลับประจำตู้** = HMAC-SHA256(master key, box_id)
  - master key อยู่บนเซิร์ฟเวอร์เท่านั้น ไม่เคยลงตู้
  - ตู้เก็บแค่รหัสลับของตัวเอง (เขียนลงบอร์ดตอนผลิต + เปิด flash encryption ของ ESP32 ถ้าทำได้)
- ตู้แต่ละตู้รู้แค่ `box_id` + รหัสลับของตัวเอง → ถ้าตู้หนึ่งโดนแกะ ตู้อื่นไม่เสียหาย

**ทุกคำขอที่ตู้ส่ง ใส่ header 4 ตัว**

```
X-Box-Id:     BX-00042
X-Timestamp:  1761123456          (วินาที, UTC)
X-Nonce:      9f2c41ab77e0         (สุ่มใหม่ทุกครั้ง)
X-Signature:  HMAC-SHA256(รหัสลับตู้, METHOD | PATH | TIMESTAMP | NONCE | SHA256(BODY)) เป็น hex
```

**เซิร์ฟเวอร์เช็ก**
- ลายเซ็นตรง → ใช่ตู้จริง
- เวลาห่างจากเวลาเซิร์ฟเวอร์ไม่เกิน ±60 วิ
- nonce ไม่เคยใช้ใน 5 นาทีที่ผ่านมา (เก็บใน Redis / memory)
- ไม่ผ่าน → ตอบ `401` + บันทึก "ความพยายามปลอม" (ผังหน้า 18, 19)

**เวลา (นาฬิกาตู้)**
- ทุกคำตอบจากเซิร์ฟเวอร์มี `server_time` → ตู้ตั้งนาฬิกาตามทุกครั้ง
- ตอนบูตครั้งแรก นาฬิกายังไม่ตรง → คำขอ `boot` ยอมให้เวลาเพี้ยนได้ แล้วตอบเวลาที่ถูกกลับไป

**การเข้ารหัสระหว่างทาง**
- HTTPS (TLS) ทุกคำขอ + ตู้ **ปักหมุดใบรับรอง** ของเซิร์ฟเวอร์ (certificate / public key pinning) กันคนตั้งเซิร์ฟเวอร์ปลอม
- เปิด TLS session resumption → ต่อครั้งถัดไปเร็วขึ้น ประหยัดไฟ

## 📡 2. รายการ API (ฝั่งตู้)

ทุก path ขึ้นต้นด้วย `/v1/box/` · ทุกคำตอบมี `server_time` และ `config_ver`

| # | เมื่อไหร่ | Method + Path | ผังหน้า |
|---|---|---|---|
| 1 | เปิดเครื่อง / ต่อ Wi-Fi ได้ครั้งแรก | `POST /v1/box/boot` | 04, 05 |
| 2 | วันละครั้ง | `POST /v1/box/report` | 18 |
| 3 | เริ่มเวลาตรวจ + ระหว่างเวลาตรวจ | `GET /v1/box/jobs?wait=50` (long-poll) | 05, 16 |
| 4 | ได้งานแล้ว เปิดกล้องพร้อม | `POST /v1/box/jobs/{job_id}/ready` | 11 |
| 5 | สแกน QR ประจำตัวได้ / ไม่ได้ | `POST /v1/box/jobs/{job_id}/result` | 19 |
| 6 | เหตุการณ์อื่น (กดปุ่ม Boot, แบตวิกฤต) | `POST /v1/box/events` | 05 |
| 7 | **ไรเดอร์กดปุ่มส่งของหน้าตู้** (ได้ทุกเวลา) | `POST /v1/box/deliveries` | 12 (ต้องเพิ่มในผัง) |

### 2.1 `POST /v1/box/boot`

**ตู้ส่ง**
```json
{
  "fw": "1.0.3",
  "config_ver": 0,
  "reset_reason": "power_on",
  "battery_pct": 87,
  "battery_mv": 3980,
  "charging": true,
  "rssi": -61,
  "wifi_ch": 6
}
```

**เซิร์ฟเวอร์ตอบ**
```json
{
  "server_time": 1761123456,
  "config_ver": 7,
  "config": {
    "windows": [["06:00","09:00"], ["17:00","21:00"]],
    "tz": "Asia/Bangkok",
    "report_at": "23:30",
    "scan_timeout_s": 20,
    "max_attempts": 3,
    "flash_when_dark": true,
    "longpoll_wait_s": 50
  }
}
```
- `config` ส่งมาเฉพาะเมื่อ `config_ver` ของตู้ไม่ตรงกับเซิร์ฟเวอร์ (ตามประชุม : เทียบเวอร์ชันแล้วค่อยอัปเดต)

### 2.2 `POST /v1/box/report` (วันละครั้ง)

**ตู้ส่ง**
```json
{
  "fw": "1.0.3",
  "config_ver": 7,
  "battery_pct": 64,
  "battery_mv": 3790,
  "charging": false,
  "solar_mv": 0,
  "temp_c": 41,
  "rssi": -66,
  "wake_count": 38,
  "jobs_done": 2,
  "scan_fail": 1,
  "wifi_fail": 0,
  "button_presses": 3,
  "delivery_fail": 0,
  "uptime_s": 86400
}
```
- `button_presses` / `delivery_fail` (เพิ่ม 27 ต.ค.) : จำนวนครั้งที่กดปุ่มส่งของ / ส่งไม่สำเร็จ ในรอบวัน

**เซิร์ฟเวอร์ตอบ**
```json
{ "server_time": 1761209856, "config_ver": 7 }
```
- ถ้าเวอร์ชันไม่ตรง → ตอบ `config` มาด้วยแบบเดียวกับ `boot`
- `temp_c` ไว้ดูความร้อนในตู้ (เรื่องแบต) / `battery_pct` < 20 → เซิร์ฟเวอร์แจ้งเตือน (ผังหน้า 18)

### 2.3 `GET /v1/box/jobs?wait=50` (long-polling ในเวลาตรวจ)

**การทำงาน**
1. ตู้ส่งคำขอแล้วรอคำตอบ (หลับเบา Wi-Fi ค้างระหว่างรอ)
2. เซิร์ฟเวอร์**ถือคำขอไว้**สูงสุด 50 วิ
   - มีเจ้าหน้าที่สแกน QR หน้าตู้ระหว่างนั้น → **ตอบทันที** พร้อมงาน
   - ครบ 50 วิ ไม่มีงาน → ตอบ `204 No Content`
3. ตู้ส่งคำขอใหม่ทันที (ใช้การเชื่อมต่อเดิม keep-alive ไม่ต้องจับมือ TLS ใหม่)
4. หมดเวลาตรวจ → ตู้หยุดถาม → หลับลึก

**มีงาน → เซิร์ฟเวอร์ตอบ**
```json
{
  "server_time": 1761124000,
  "job": {
    "job_id": "J-8f31c2",
    "type": "inspect",
    "expires_at": 1761124060,
    "scan_timeout_s": 20,
    "attempt_max": 3
  }
}
```

**ทำไมเลือก long-polling ไม่ใช่ WebSocket / MQTT**
- ใช้ HTTP เดิม endpoint เดียวกับที่เหลือ ไม่มีระบบใหม่ให้ดูแล
- คำขอใหม่ทุก ~50 วิ ช่วยกันเราเตอร์บ้านตัดการเชื่อมต่อที่เงียบนานเกินไป
- ทางเลือก : ถ้าวัดแล้วกินไฟหรือช้าเกิน ค่อยเปลี่ยนช่วงเวลาตรวจเป็น WebSocket (wss) ได้ โดย endpoint อื่นไม่ต้องเปลี่ยน

### 2.4 `POST /v1/box/jobs/{job_id}/ready`

ตู้เปิดไฟ + กล้องเสร็จ → บอกเซิร์ฟเวอร์ → เซิร์ฟเวอร์บอกแอปเจ้าหน้าที่ให้แสดง QR ประจำตัว

```json
{ "light": "on", "flash": false }
```

### 2.5 `POST /v1/box/jobs/{job_id}/result`

**ตู้ส่ง (ทุกครั้งที่ลอง ทั้งผ่านและไม่ผ่าน)**
```json
{
  "attempt": 1,
  "read_ok": true,
  "qr_text": "SMMB-O1.eyJqIjoiSi04ZjMxYzIiLCJ1IjoiVS0wMDcxIiwiZSI6MTc2MTEyNDAzMH0.Zx9k…",
  "read_ms": 2400,
  "flash": false
}
```
- อ่านไม่ได้ภายในเวลา → `"read_ok": false, "qr_text": null`
- ตู้**ไม่ตัดสินเอง**ว่าผ่านไหม แค่ส่งสิ่งที่อ่านได้ เซิร์ฟเวอร์เป็นคนตรวจ (ผังหน้า 19)

**เซิร์ฟเวอร์ตอบ**
```json
{ "server_time": 1761124012, "status": "pass" }
```
```json
{ "server_time": 1761124012, "status": "retry", "attempts_left": 2 }
```
```json
{ "server_time": 1761124012, "status": "fail" }
```
- ตู้ใช้ `status` แสดงไฟ : pass = เขียว · retry = กะพริบ (สแกนใหม่) · fail = แดง
- ห้ามเก็บผลไว้ส่งทีหลังถ้าส่งไม่ได้ (ตามประชุม : ไม่บันทึกออฟไลน์) → ทิ้ง + นับใน `scan_fail` ของรายงานรายวัน

### 2.6 `POST /v1/box/events`

```json
{ "type": "wifi_reset_button" }
```
- ประเภท : `wifi_reset_button` · `battery_critical` (< 5% ก่อนดับ) · `camera_error`
- ส่งแบบ "พยายามครั้งเดียว" ส่งไม่ได้ก็ไม่เป็นไร

### 2.7 `POST /v1/box/deliveries` (ไรเดอร์กดปุ่มหน้าตู้ — เพิ่ม 27 ต.ค.)

**ฮาร์ดแวร์ (ให้พี่ตั๋งดู)**
- ปุ่มกดกันน้ำที่หน้าตู้ ต่อขาที่**ปลุก ESP32 จากหลับลึกได้** (RTC GPIO / ext0) → กดได้ทุกเวลา แม้นอกเวลาตรวจ
- ใช้ไฟสถานะเดิมบอกผลให้ไรเดอร์เห็น
- คนละปุ่มกับปุ่ม Boot บนบอร์ด (ปุ่ม Boot = ล้าง Wi-Fi อยู่ในตู้)

**การทำงาน**
1. กดปุ่ม → ตู้ตื่น → ไฟกะพริบ "กำลังส่ง"
2. รอ ~3 วิ เผื่อกดซ้ำ แล้วรวมเป็นคำขอเดียว (`press_count`) · ระหว่างส่งไม่รับกดใหม่ — กันเด็กกดเล่นจนแบตหมด
3. ต่อ Wi-Fi → ส่งคำขอ → ไฟบอกผล → หลับต่อ (ในเวลาตรวจกลับไปถือ long-poll — ถ้ากำลังถือ long-poll อยู่ ให้เปิดการเชื่อมต่อที่สองส่งคำขอนี้ ไม่ต้องรอ)
4. หลังส่งเสร็จ ไม่รับกดใหม่ ~30 วิ

**ตู้ส่ง**
```json
{ "pressed_at": 1761125000, "press_count": 1, "battery_pct": 63 }
```

**เซิร์ฟเวอร์ตอบ**
```json
{ "server_time": 1761125003, "status": "ok" }
```
```json
{ "server_time": 1761125003, "status": "limited" }
```
```json
{ "server_time": 1761125003, "status": "service_closed" }
```
- ไฟ : ok = เขียว · limited (กดถี่เกินเพดานต่อตู้ — นับรวมกับการสแกน QR ของไรเดอร์) = ส้มกะพริบ · service_closed / ส่งไม่ได้ = แดง
- `ok` → เซิร์ฟเวอร์บันทึกการส่งของ (`method: button`) + แจ้งเจ้าของบ้าน "มีของมาส่ง (กดปุ่มหน้าตู้)"
- คำขอซ้ำ (เน็ตกระตุก) → `X-Nonce` เดิม = กุญแจกันซ้ำ เซิร์ฟเวอร์ตอบผลเดิม
- คำขอนี้มีลายเซ็นตู้ = พิสูจน์ว่ามีคนอยู่หน้าตู้จริง

## 🏷️ 3. รูปแบบ QR แต่ละแบบ

### 3.1 QR หน้าตู้ (ใบ 1 / ใบ 2)

**ข้างใน QR = ลิงก์**
```
https://smmb.app/b/BX00042-1-K7M2QX
                   │       │ └─ ลายเซ็นย่อ 6 ตัว = HMAC(คีย์เซิร์ฟเวอร์, box_id|ใบที่|รุ่น) ตัดสั้น
                   │       └─── ใบที่ (1 / 2)
                   └─────────── รหัสตู้
```
- ไรเดอร์สแกนด้วยกล้องมือถือ → เปิดลิงก์ → หน้าส่งของ (หรือไรเดอร์กดปุ่มหน้าตู้แทนก็ได้ §2.7)
- เจ้าหน้าที่สแกนในแอป → แอปส่งข้อความทั้งหมดให้เซิร์ฟเวอร์เช็กลายเซ็น → **ไม่ตรง = "QR นี้ไม่ใช่ของระบบ"** (อาจถูกแปะทับ)
- ออกใบใหม่ → เพิ่ม "รุ่น" → ลายเซ็นเปลี่ยน → ใบเก่าใช้ไม่ได้ทันที

**รหัสสำหรับพิมพ์ (ใต้ QR)**
- รหัสสุ่ม 8 ตัว แยกต่อใบ เช่น `H4KD-9TRW`
- ใช้แค่ตัวอักษรที่ไม่สับสน (ไม่มี 0/O, 1/I/L) · พิมพ์เล็กใหญ่ได้
- พิมพ์ผิดหลายครั้งติดกัน → หน่วงเวลา กันเดารหัส

**พิมพ์จริง** : QR ระดับแก้ข้อผิดพลาดสูงสุด (H) · ขนาดใหญ่พอสแกนจากระยะแขน · เคลือบกันแดดกันน้ำ

### 3.2 Activate QR (ในตู้)
```
https://smmb.app/a/8Q3JX7KD2MZP4W9R
```
- รหัสสุ่มยาว 16 ตัว (เดาไม่ได้) · ใช้ได้**ครั้งเดียว** · ผูกแล้วรหัสนี้ตายทันที

### 3.3 QR ประจำตัวเจ้าหน้าที่ (เปลี่ยนทุก 30 วิ)

**ใครสร้าง** : เซิร์ฟเวอร์ (ไม่เก็บรหัสลับไว้ในมือถือ) → แอปขอ token ใหม่ทุก 30 วิ ระหว่างอยู่หน้า QR

**ข้างใน QR**
```
SMMB-O1.<ข้อมูล>.<ลายเซ็น>
ข้อมูล = { "j": "J-8f31c2", "u": "U-0071", "e": 1761124030 }
          job_id ของตู้นี้   เจ้าหน้าที่    หมดอายุ (30 วิ)
```
- **ผูกกับ job_id** → ใช้ได้แค่ตู้ที่เพิ่งสแกน QR หน้าตู้เท่านั้น เอาไปใช้ตู้อื่นไม่ได้
- หมดอายุใน 30 วิ → ถ่ายรูปเก็บไว้ใช้ทีหลังไม่ได้
- เซิร์ฟเวอร์เช็ก (ผังหน้า 19) : ลายเซ็นถูก · `j` ตรงกับงานของตู้นี้ · `u` ตรงกับคนที่สแกน QR หน้าตู้ · ยังไม่หมดอายุ

## ⚠️ 5. กรณีผิดพลาด

| เหตุการณ์ | ตู้ทำอะไร |
|---|---|
| ต่อเซิร์ฟเวอร์ไม่ได้ (ตอน report) | ลองใหม่ 3 ครั้ง ห่าง 5 / 15 / 45 วิ → ไม่ได้ก็หลับ ลองรอบถัดไป |
| ต่อไม่ได้ระหว่างเวลาตรวจ | ลองใหม่ทุก 30 วิ (เซิร์ฟเวอร์จะแจ้งตู้หลุดเองถ้าเกิน 10 นาที) |
| ได้ `401` (ลายเซ็นไม่ผ่าน) | sync เวลาจาก `server_time` แล้วลองใหม่ 1 ครั้ง → ยังไม่ผ่าน = ไฟแดง + ส่ง event |
| ได้ `410` (job หมดอายุ) | ปิดกล้อง กลับไปรองานต่อ |
| ส่งผลสแกนไม่ได้ | ทิ้ง ไม่เก็บไว้ส่งทีหลัง |
| ส่งการกดปุ่มส่งของไม่ได้ | ลองใหม่ 3 ครั้ง ห่าง 5 / 15 / 45 วิ (ไฟกะพริบรอ) → ไม่ได้ = ไฟแดง + ทิ้ง + นับใน `delivery_fail` (ไม่เก็บไว้ส่งทีหลัง) |
| คำขอซ้ำ (เน็ตกระตุก ส่งซ้ำ) | ใช้ `job_id + attempt` เป็นกุญแจกันซ้ำ (ปุ่มส่งของใช้ `X-Nonce`) เซิร์ฟเวอร์ตอบผลเดิม |

## 🔋 6. เรื่องไฟที่เกี่ยวกับโปรโตคอล

- ตื่นแต่ละครั้ง : ต่อ Wi-Fi (จำช่อง + IP ตายตัว) → TLS (ใช้ session resumption) → ส่ง 1 คำขอ → หลับ
- ข้อมูลแต่ละครั้ง < 1 KB → เวลาส่งน้อยมาก ส่วนที่กินไฟคือการต่อ Wi-Fi + TLS
- long-poll ในเวลาตรวจ : คำขอเล็ก ๆ ทุก ~50 วิ บนการเชื่อมต่อเดิม → ให้พี่ตั๋งวัดไฟจริงช่วงนี้
- กดปุ่มส่งของ 1 ครั้งนอกเวลาตรวจ = ตื่น + ต่อ Wi-Fi + TLS 1 รอบ (เท่ากับรายงานรายวัน 1 ครั้ง) → บ้านที่ของมาส่งบ่อยกินไฟเพิ่ม · ช่วงไม่รับกดซ้ำ (~30 วิ) ช่วยกันกดเล่น

## ❓ 7. ที่ต้องตัดสิน / ทดสอบ

1. ESP32-CAM มี RAM พอทำ TLS + กล้อง + JSON พร้อมกันไหม (ปกติพอ ถ้าใช้บอร์ดที่มี PSRAM)
2. วัดเวลา : ตู้ได้งาน → `ready` ใช้กี่วิ (เป้า 1–3 วิ)
3. เราเตอร์บ้านทั่วไปตัดการเชื่อมต่อเงียบหลังกี่วิ (ปรับ `longpoll_wait_s` ให้สั้นกว่านั้น)
4. ชื่อโดเมนจริง (ในเอกสารใช้ `smmb.app` เป็นตัวอย่าง)
5. ฝั่งแอปเจ้าหน้าที่จะรู้สถานะตู้ด้วยการถามทุก 1 วิ หรือ SSE
6. ปุ่มส่งของ (27 ต.ค.) : ขาว่างบน ESP32-CAM ที่ปลุกจากหลับลึกได้ (กล้องใช้ขาไปเยอะ) · ปุ่มกันน้ำแบบไหน · ไฟบอกผลแยกสีได้ไหม · วัดไฟต่อการกด 1 ครั้ง · ช่วงไม่รับกดซ้ำกี่วินาที · ส่งไม่ได้ควรลองใหม่ไหม
